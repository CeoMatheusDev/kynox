## 3. Findings

Severity: **P0** data loss/boot/security, **P1** alpha blockers,
**P2** subsystem integration, **P3** tests/observability, **P4** docs/tooling.

### P1 — alpha blockers

#### A-01 · Version identifiers disagree and have no single source of truth — P1
Evidence:
- `build.zig.zon:3` → `.version = "0.1.0-dev.3"`
- `boot/uefi/main.zig:51` → `loader_version = "0.1.0-dev.1"`
- `kernel/main.zig:214` → `kernel_version = "0.1.0-dev.1"`
- planned release: `0.1.0-alpha.1`
- Git history has **one** commit and **no tags**, so `-dev.3`/`-dev.1` do not
  correspond to any published increment.

Impact: release artifacts cannot be identified; `kernel` logs `0.1.0-dev.1`
while the package manifest claims `0.1.0-dev.3`. Alpha criterion
"version of the compiler/artifact documented" cannot be met with ambiguous
version strings.

Direction (not implemented in this audit): one `VERSION` file or a single
`build.zig` constant injected into both modules with `addOptions`, printed by
loader and kernel, asserted by a host test.

#### A-02 · Boot/run validation depends on QEMU + OVMF, which are not installed here — P1
Evidence: `tests/integration/boot-qemu.sh:236-305` searches OVMF in seven
locations and exits with a diagnostic when absent; no `qemu-system-x86_64`
binary exists in this environment; package mirrors are unreachable. The only
reachable distributors are GitHub/PyPI/npm, none of which ship a Linux QEMU
system emulator.

Impact: the alpha gate "boot UEFI reproduzível / boot test in QEMU executed"
**remains unverified**. It is not a code defect; it is an environment
constraint that must be closed by the maintainer on a machine with
QEMU/OVMF. This audit does not claim any QEMU result.

**Recorded attempt (remediation stage 4).** `zig build qemu-test`,
`qemu-storage-test` and `qemu-interactive-test` were executed and all three stop
at the same point: `qemu-boot-test: no OVMF firmware found` (exit 2).
`qemu-system-x86_64` is not installed either, and installing it is not possible
in this sandbox (no privileges for `apt-get update`, restricted outbound
network). The procedure and the attempt table live in `docs/validation/qemu.md`.
Nothing was simulated.

**Update (runtime-validation task, 2026-10-31).** A root-free provisioning
script (`scripts/provision-qemu.sh`) now downloads a static QEMU and OVMF into
`.tools/`, and a CI workflow installs both on the runner. The script fails here
one step earlier than the suites: `SSL_ERROR_SYSCALL` contacting
`release-assets.githubusercontent.com` (the release assets host). The suites
still exit 2 and still record no run; see `docs/validation/qemu.md` §8 for the
verbatim log. The finding stays **open**.

#### A-03 · ACPI/MADT is implemented but never consumed by the boot path — P1
Evidence: `kernel/arch/x86_64/acpi.zig` parses RSDP/XSDT/MADT and exposes
`local_apic_base` (`acpi.zig:98,197,245`), with 91 arch tests covering the
parsers. `kernel/main.zig` does **not** reference the ACPI module at all;
`kernel/main.zig:2496-2500` maps and initializes the LAPIC at the compile-time
constant `apic.apic_base = 0xFEE00000` (`apic.zig:41`), whose own comment calls
it "the default address of QEMU/OVMF".

Impact: a firmware that advertises a different LAPIC base will misbehave, and
`handoff.acpi_rsdp_address` is carried but unused. This is the concrete
substance behind the "fixed hardware assumptions" gap in the status
inventory; the inventory wording was accurate, but the fact that MADT is not
wired in at all was not stated explicitly anywhere.

**Correction (same date, during remediation).** The sentence "91 arch tests
covering the parsers" was wrong. `kernel/arch/x86_64/root.zig` did not import
`acpi.zig`, so the ACPI tests were compiled into no test artifact and had never
executed. After adding the import the suite reported 100 arch tests (91 + 9 ACPI)
and then 112 with the new discovery tests. The finding stands and was worse than
described.

**Resolved in part.** `discoverAcpi` in `kernel/main.zig` now reads the MADT
through the loader-provided RSDP before CR3 is replaced, installs the validated
LAPIC base with `apic.setBase`, and records the IOAPICs and interrupt source
overrides. The IOAPIC redirection table is not programmed and the overrides do
not affect routing; see `docs/specs/acpi-platform.md`. No runtime validation was
possible (A-02).

**Update (runtime-validation task, 2026-10-31).** The overrides now affect
routing for the two ISA lines the kernel consumes: `installIoApic` maps the
first usable controller, masks every entry, programs IRQ0 (PIT) and IRQ1
(keyboard) with the GSI/polarity/trigger from `acpi.isaRoute`, and leaves them
masked. Delivery still comes from the 8259 unless the build option
`-Dioapic-delivery=true` is set, and that option has never been booted. The
finding remains open for runtime evidence.

#### A-04 · Native ABI has three different declared versions and no kernel-side version — P1
Evidence:
- `sdk/src/syscall.zig:20` → `abi_version = 13` ("ABI VSC-0001, versão 13")
- `sdk/src/syscall.zig:51` → error catalog documented as "VSC-0001 v12"
- `sdk/README.md:7` → "VSC-0001, versão 9"
- `kernel/arch/x86_64/syscall.zig` → **no** ABI version constant, and the
  specification file it is supposed to reference did not exist.

Impact: the alpha criterion "native ABI documented" is not met by the SDK
alone; there is no authoritative, versioned document and the kernel cannot
report or enforce the ABI level it implements.

#### A-05 · SDK README contradicts the tree — P1 (for release honesty)
Evidence: `sdk/README.md` states "implementado, aguardando compilação e
validação", instructs the reader to check out `feat/native-sdk` and validate
"no Fedora", claims F6 raster "ainda não está conectado ao framebuffer do
boot" and "não foi compilada nem executada no ambiente do agente", and says
"Nenhum novo número de syscall foi introduzido" while the SDK now exports 22
calls (numbers 1–23, 12 reserved).

Impact: a public-facing document that contradicts the code and the release
notes. Resolved in this change (see §5).

#### A-06 · Dangling documentation references from source and SDK — P1 (for docs completeness)
Evidence (verified by scanning every `.zig/.md/.sh/.json` for doc paths):
- `docs/specs/boot-handoff-spec.md` — referenced by `shared/handoff.zig:27` and `shared/elf64.zig`; did not exist.
- `docs/specs/syscall-abi.md` — referenced by `sdk/README.md`; did not exist.
- `docs/adr/ADR-F04-block-driver-proposta.md` — referenced by `kernel/arch/x86_64/virtio_blk.zig:37`; did not exist. `strategy.md` §5 designates `docs/decisions/` for ADRs, so the cited path is also inconsistent with the project convention.

Resolved in part in this change: both `docs/specs/` documents are now written
from the code. The ADR reference was corrected to describe the pending work
without pointing at a non-existent file (the ADR itself is still to be
written; see §6, increment 6).

### P2 — subsystem integration

#### A-07 · Two parallel VirtIO/virtqueue implementations, plus a test-only stub — P2
Evidence:
- `kernel/arch/x86_64/virtio.zig` (852 lines, split-queue layout, DMA descriptor
  adapter, 20+ host tests) — used by `kernel/main.zig:52` for
  `probeVirtqueueLayout()` and by `virtio_net.zig`.
- `kernel/drivers/kvdi/` (transport, virtqueue, block, containment) — the path
  that performs real I/O through `kernel/main.zig:bringUpVirtioDevices()`.
- `kernel/arch/x86_64/virtio_blk.zig` — legacy stub that unconditionally returns
  `error.NotImplemented`; it is not referenced by the kernel entry path and
  survives only because `kernel/arch/x86_64/root.zig:44` imports it to run its
  tests.

Impact: two queue implementations can drift; the stub is dead code that costs
review attention. Decision required: either delete the legacy stub (and its
import in `root.zig`), or document it as a compatibility shim with an owner.
Not removed in this audit — removal changes the test root and belongs to its
own increment.

#### A-08 · Fixed LAPIC base and IOAPIC absence (see A-03) — P2
Tracked once under A-03 to avoid double counting; listed here because the
remediation is integration work (wire MADT discovery into `installSmp`).

#### A-09 · `kernel/main.zig` mixes initialization, probes, reports and benchmarks — P2
Evidence: 4,738 lines containing `kynox_kmain` plus ~40 probe/report functions
(`probeDmaWindow`, `bringUpVirtioDevices`, `verifyVirtioBlockPersistenceProbe`,
`benchmarkFramebufferWrites`, `selfTest`, `reportXxx`…).

Impact: `AGENTS.md` §4.1 says "o kernel deve integrar subsistemas; não
concentre novas implementações em `kernel/main.zig`". The current file is the
integration harness for the alpha (which is defensible), but it is already the
repository's maintenance hotspot. Proposal: extract the boot-time probes into
`kernel/diagnostics/` (or `kernel/selftest/`) without changing behavior, in
one increment guarded by the boot markers consumed by `boot-qemu.sh`.

#### A-10 · User address window is centralized and dynamic — resolved, no action
Checked and **not** a finding: virtual addresses are computed from
`user_window_base + usermode.<offset>` (`shared/usermode.zig:35-52`), and the
kernel chooses a base that avoids its own identity-mapped image. `paging.
isUserRange()` validates every page of every user buffer before dereferencing
(`syscall.zig` uses it in 13 call sites, including the cross-process copy).

### P3 — tests and observability

#### A-11 · No CI configuration — P3
No `.github/`, no equivalent. The build and test commands are reproducible
locally (proven above) but nothing enforces them.

#### A-12 · Bootloader has zero host tests — P3
`boot/uefi/` is 1,303 lines with no `test` block; its logic (file system
lookup, ELF placement, memory map capture, framebuffer description) is only
exercised end-to-end by a QEMU run that cannot happen here. `AGENTS.md`
requires host tests for pure logic; the KNB parsers are the obvious
candidates.

#### A-13 · Eight files are unreachable from the build graph and from scripts — P3
Verified zero inbound references (excluding self):
`tests/f9/verify-integration.sh`, `tests/integration/log-assertions-test.sh`,
`tests/integration/f4_physblk_knv_integration.zig`,
`tests/user_apps/minimal_test.zig`, `tests/user_apps/test_fs.zig`,
`kernel/fs/test_ramfs_runner.zig`, `tools/benchmarks/syscall_bench.zig`,
`tools/scripts/recovery-mode.sh`.

Impact: `docs/PROJECT_STATUS.md` said "multiple built test applications";
the build embeds exactly two (`user/hello.zig`, `user/client.zig`, converted
by `tools/bin2zig.zig`). `tools/benchmarks/syscall_bench.zig` is not built by
any target, so no syscall benchmark can be run today despite the
"performance/observability" entry claiming benchmark source. Status text
corrected in this change; files left in place for a deliberate keep/delete
decision.

#### A-14 · QEMU scripts are the only integration evidence and are not reproducible off-machine — P3
`tests/integration/boot-qemu.sh` asserts ~45 serial markers (handoff, GDT/IDT,
NX, PCI scan, DMA window, virtqueue, timer, PS/2, graphics redraw, filesystem,
KNV commit/recover, KPK, tasks, native ELF execution, page permissions). This
is a strong contract, but it is only meaningful when executed. No result has
ever been recorded in the repository (no CI artifacts, no release notes).

### P4 — documentation and tooling

#### A-15 · `.gitignore` contains a stray Markdown fence — P4
`.gitignore` ends with a literal ` ``` ` line (line 7), the residue of a
paste. It ignores a file named ``` and adds noise. Fixed in this change.

#### A-19 · Boot image builder documented a file name it does not write — P4
`tools/fatimg.zig` wrote `KYNOXK.ELF` into `/boot` (verified in the generated
image) while its module documentation advertised `/boot/kynox-kernel.elf`, a
name the loader (`boot/uefi/main.zig:54`, `\boot\kynoxk.elf`) would never find.
Documentation-only defect; fixed in this change.

#### A-16 · `docs/PROJECT_STATUS.json` used a status vocabulary that AGENTS mandates against — P4
The JSON used `partial` / `planned`, which are not in the mandated set
(`not_started`, `scaffolding`, `in_progress`, `implemented`, `integrated`,
`validated`, `blocked`), and carried no per-subsystem `tests` or `validation`
result fields. Migrated to schema v2 in this change (see §5).

#### A-17 · `README.md` promised behavior of test targets without recorded results — P4
The README was accurate about *which* targets exist (`check` = unit + boot +
storage, interactive separate — verified against `build.zig:600-616`), but
carried no statement of what had actually been executed. Now carries a dated
verification record.

#### A-18 · `logo_kynox.jpg` (310 KB binary) — P4, no action
Intentional project asset; not an artifact of the build. Kept.

### Verified and found correct (no action)

- `zig build` and `zig build test` succeed from a clean tree with Zig 0.17.0;
  `zig-out/` and `.zig-cache/` are ignored, the working tree stays clean.
- No `TODO`/`FIXME`/`XXX`/`HACK` markers anywhere in `*.zig`/`*.s`/`*.sh` —
  the "no stubs presented as implementations" rule is respected. The one stub
  that exists (`virtio_blk.zig`) is explicitly documented as a stub and
  returns an error.
- W^X is enforced at the point where page flags are produced
  (`paging.zig:746-760`, `userPageEntryFlags`), with tests asserting that a
  user page is never writable and executable (`paging.zig:1109-1120`); the
  kernel refuses to boot without NX (`main.zig` fatal path).
- Every user-supplied pointer/length pair in the syscall surface goes through
  `paging.isUserRange()` (or `isUserRangeIn()` for cross-process copies) before
  use; overflow is checked with `std.math.add`.
- The handoff contract is versioned, size-checked and validated field by field
  (`shared/handoff.zig:266-281`), and the kernel verifies the entry point
  against the handoff (`main.zig`, "entry mismatch" fatal path).
- The build graph orders the image before the QEMU scripts that read it, and
  the storage suite is serialized behind the boot suite (comment at
  `build.zig:585-589`) — a real race that the author already fixed.
- `build.zig.zon` declares **no** external dependencies; there is no libc, no
  vendored third-party loader, and no Wine/WSL/Proton-style component. The
  own-technology policy in `KYNOX_NATIVE.md` is respected in the tree.
- Legacy-vs-active block driver confusion is documented in `README.md`,
  `PROJECT_STATUS.md` and the stub itself — consistent across all three.

## 6. Prioritized execution plan

### P0 — none found
No corruption, data-loss or privilege-escalation defect was identified in the
inspected paths. This is **not** a statement that the kernel is free of P0
defects: A-02 means the running system has never been observed in this
environment, and the syscall/ELF/IPC surface has not been fuzzed.

### Increment 1 — Reproducibility record (P1, no product behavior)

## 7. Limitations of this audit

- No QEMU/OVMF: zero runtime evidence about the produced image.
- Single host (2 vCPU/3 GiB, TCG-only if QEMU were available): no performance
  claim of any kind is made, and the existing benchmark sources were not run.
- No fuzzing, no static analysis tool beyond the compiler, no KVDI protocol
  review against VirtIO 1.2, no concurrency proof.
- Maturity percentages in `docs/PROJECT_STATUS.*` remain estimates; this audit
  deliberately did not move them.
